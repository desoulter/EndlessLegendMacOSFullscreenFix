# Диагностика разницы потребления при 2048×1330

Основной протокол — неподвижная сцена туториала с отметкой F8. Фоновые сценки
главного меню меняются между запусками и могут давать существенно разную нагрузку.
Записи меню подтверждают работу наблюдателя и параметры рендера, но не позволяют
оценить влияние патча на потребление в одинаковой сцене.

## Что установлено по исполняемому файлу

В Unity 5.3.6p1 функция `MakeNewContextGL` (0x101095bd0) и
`SetupDefaultContextState` (0x101095ea0) устанавливают `kCGLCPSwapInterval = 0`.
`GetActualTargetFrameRate()` (0x100ab08f0) при положительном VSync использует
частоту режима экрана, делённую на VSyncCount, вместо скриптового targetFrameRate.
Начальная установка swap interval в ноль не означает, что он остаётся нулевым:
в записанном original от 7 ноября фактический `swap_interval = 1` и VSync включён.
Поэтому запись `TargetFrameRate=100` в Registry.xml не доказывает фактический
лимит 100 кадров/с. Нужны целевой FPS движка и частота present в обоих режимах.

`SetResolutionImmediate` (0x101087d70) для fullscreen без смены режима дисплея
проверяет различие выбранного разрешения и размеров дисплея. При различии оно
создаёт `SetupDownscaledFullscreenFBO` (0x101087710). `PreBlit` (0x1010883c0)
разрешает MSAA в текстуру, затем рисует её в framebuffer окна. Оригинальный
fullscreen со сменой режима дисплея может обойти этот промежуточный путь.
Это подтверждённое различие ветвей, а не доказательство величины их стоимости.

## Два прогона в одной сцене туториала

Команды выполняются из каталога репозитория. Закройте игру перед каждой командой.
Настройки сохраняйте одинаковыми: 2048×1330, Fantastic, тот же VSync, большой UI,
тот же источник питания. Сначала дайте компьютеру остыть до близкого состояния.

```sh
sudo -v
python3 tools/render_probe.py record --mode original --power --measure 180
```

Утилита сама выбирает оригинальный fullscreen, временно подключает наблюдатель и
запускает логгер. Когда появится `Run folder:`, вручную запустите игру через Steam.
Дойдите до одного выбранного шага туториала с видимой картой. Лучше использовать
одно и то же сохранение. Зафиксируйте одинаковые положение и масштаб камеры,
выбранный отряд и открытые подсказки/панели. Не перемещайте юниты и не заканчивайте
ход во время измерения.

Нажмите **F8 прямо в игре** (на Mac обычно **Fn+F8**). Прозвучит сигнал. Логгер
пропустит 30 секунд стабилизации, затем измерит 180 секунд. После второго сигнала
выйдите из игры. В Terminal переключаться не нужно: это работает и в original,
где Cmd-Tab ограничен. F8 используется наблюдателем только с флагом `--measure`;
остальные клавиши передаются игре без изменений. Повторные F8 не сдвигают начало.

После охлаждения:

```sh
sudo -v
python3 tools/render_probe.py record --mode patched --power --measure 180
```

Повторите тот же шаг туториала, камеру и нажатие F8. Наблюдатель **не меняет** разрешение,
MSAA, VSync или ограничение кадров. Полноэкранный режим после записи остаётся
выбранным через `--mode`; наблюдатель после выхода удаляется автоматически.

Записи имеют метки `original-probe-tutorial-*` и `patched-probe-tutorial-*` в `benchmark-results/`.
Старые результаты сохраняются. Прогон включает обычную телеметрию и дополнительные
файлы `render-probe-PID.jsonl`. После первой секунды активного рендера CSV получает:

| Поле | Что означает |
| --- | --- |
| `present_fps` | Завершённые CGLFlushDrawable в секунду, не физически показанные кадры |
| `present_flush_ms` | Среднее CPU-время самого CGLFlushDrawable, не GPU-время кадра |
| `render_width`, `render_height` | Размеры рендера в ScreenManager |
| `present_viewport_width`, `present_viewport_height` | GL viewport перед present |
| `surface_samples` | GL_SAMPLES поверхности framebuffer 0 перед present |
| `msaa_fbo_samples`, `msaa_fbo_width`, `msaa_fbo_height` | Параметры игрового MSAA-буфера |
| `quality_msaa`, `quality_vsync` | Действующие параметры QualitySettings |
| `target_fps_script`, `target_fps_engine` | Скриптовый и вычисленный движком лимиты |
| `swap_interval` | Реальный OpenGL swap interval |
| `probe_query_ms` | Длительность опроса параметров рендера раз в секунду |
| `measurement_elapsed_s`, `measurement_phase` | Время от начала отмеченного измерения и фаза |

Отсутствующие или старые данные FPS не подставляются в новые строки. Сравнение
последних прогонов поддерживает и новые метки:

```sh
python3 tools/gpu_benchmark.py compare --output benchmark-results/tutorial-comparison.html
```

Если оба прогона отмечены, сравнение автоматически совмещает их по началу
измерения после F8 и стабилизации. Меню, загрузка и время до контрольного шага
не попадают в отчёт. Отмеченный прогон нельзя смешать с неотмеченным. Если F8 не
нажата или игра закрыта раньше окончания окна, запись сохраняется, но не выбирается
как пригодная для сравнения. Логи Unity и Diagnostics также сохраняются в папке
записи. `--warmup` меняет период стабилизации, по умолчанию он равен 30 секундам.

## Отдельные эксперименты после наблюдения

Чтобы проверить стоимость MSAA игрового промежуточного буфера, можно записать:

```sh
sudo -v
python3 tools/render_probe.py record --mode patched --msaa-cap 0 --power
```

Этот эксперимент сохраняет выбранное разрешение и Retina, но **снижает качество
MSAA промежуточного буфера**. Он не является готовой оптимизацией с тем же
качеством. Меняется только выделение color/depth в двух известных fullscreen
местах Unity. Другие MSAA-буферы не ограничиваются. В логе `allocation` должны
быть `fullscreen_experiment: true`, `passed_samples: 0`, `actual_samples: 0`.
При отсутствии этого подтверждения считать эксперимент применённым нельзя.
Доступны также `--msaa-cap 2` и `--msaa-cap 4`.

Если FPS различается, сравните **оба** режима при общей верхней границе 60:

```sh
python3 tools/render_probe.py record --mode original --fps-cap 60 --power --measure 180
python3 tools/render_probe.py record --mode patched --fps-cap 60 --power --measure 180
```

Нужно снова выполнить каждый прогон отдельно с одинаковой сценой и охлаждением.
Наблюдатель ограничивает частоту только в этом явно выбранном эксперименте.
Ожидание выполняется после реального swap, с учётом уже затраченного на него
времени: дополнительное ожидание перед swap могло бы пропустить vblank и дать
около 40 вместо 60 кадров/с на дисплее 120 Гц. Для медленного кадра дополнительной
паузы нет. Это не гарантирует 60 FPS, если сама игра работает медленнее.
Во время отмеченного измерения не продолжайте урок, не закрывайте подсказки,
не перемещайте камеру/юниты и не завершайте ход. Лучше загрузить одно сохранение.

## Восстановление и ограничения проверки

У наблюдателя отдельный manifest в `ContextFix/render-probe/`. Он добавляет только
зависимость в свободное место Mach-O, свою dylib и конфигурацию. Production-helper,
его manifest, игровые настройки, аудиопатч и шейдеры наблюдатель не меняет.
При снятии возвращаются точные байты и права исполняемого файла до наблюдения.
Сохраняются диагностические логи и копия player до установки наблюдателя.

Если логгер прерван при работающей игре, наблюдатель остаётся установленным до
её закрытия. Закройте игру и выполните:

```sh
python3 tools/render_probe.py remove
```

Перед обычной установкой/снятием fullscreen-патча сначала снимайте оставшийся
наблюдатель этой командой. Изменённые после установки файлы не перезаписываются.
Наблюдатель рассчитан строго на проверенный Intel player; в другом бинарнике
внутренние смещения не используются.

### Исправление совместимости наблюдателя с MSAA-патчем

Первый patched-прогон с наблюдателем от 7 ноября дал чёрный экран: два dyld
перехватчика `glRenderbufferStorageMultisampleEXT` не скомбинировались, и запрос
8 samples дошёл до драйвера без ограничения до 4. В логе allocation были
`passed_samples: 8` и фактические размеры 0×0. Этот прогон непригоден для сравнения.

Исправленный наблюдатель в режиме patched сам сохраняет штатное ограничение
драйвера в тех же двух fullscreen местах, прежде чем применить явно выбранный
эксперимент. В original он не ограничивает запросы. Лог allocation теперь содержит
`driver_max_samples`, `safety_clamp`, `fullscreen_allocation` и `patched_mode`.
Проверка с настоящим dyld и подставным GL-драйвером выполняет код наблюдателя
под x86_64, включая определение вызывающего места по стеку, отдельно и рядом
со вторым перехватчиком. Графический сеанс для этого теста не нужен.

После исправления patched был записан повторно; затем оба режима прошли
контрольную проверку на одном шаге туториала. Логгер помечает записи с ненулевым MSAA framebuffer
и вложением размера 0×0 как непригодные для сравнения; их исходные данные сохраняются.

Сборка, загрузка через Rosetta и точный откат на временной копии проверяются
автоматически. Оба контрольных прогона выполнены в обычном графическом сеансе.
Production-ограничитель также проверен при запуске через Steam без наблюдателя.
Результаты и ограничения сравнения — в [журнале исследования](POWER-INVESTIGATION.ru.md).
Другие конфигурации требуют отдельной проверки в игре.
